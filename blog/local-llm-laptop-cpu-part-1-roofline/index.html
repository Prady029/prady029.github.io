A 35B Coding Agent on a Laptop CPU, Part 1 of 8: Do the Napkin Math First

Before downloading a single model: what an agent's traffic looks like, what this CPU can physically do, and why only a Mixture-of-Experts model was ever going to be viable.

#llm-inference#llama.cpp#cpu#roofline#moe

Part 1 of 8 in the series. Next: Part 2: Most Tuning Knobs Don't Matter (and Some Backfire) (coming soon).

Over three days I turned an AMD Ryzen 7 7730U laptop (8 Zen 3 cores, 24 GB DDR4-3200, integrated graphics only) into a local coding-agent host: the terminal agent pi talking to a llama.cpp server running a 35-billion-parameter model on the CPU alone. This series is the field notes. Almost every win came from understanding the bottleneck rather than from tuning flags, so this first part covers the groundwork: the workload, the silicon, and the model shape the two of them allow.

The mindset

I approached this like any capacity problem in production inference. Three rules held throughout:

  1. Characterize the workload before choosing the system. An agent's traffic pattern is nothing like a chatbot's.
  2. Know which resource is saturated. On a CPU, the bottleneck is either compute (FLOPs), memory bandwidth (GB/s), or heat (watts). Each phase of inference hits a different one.
  3. Every claim gets a benchmark, including the folklore. Several widely repeated tips made things worse here.

Each section in this series ends with the lesson it taught, since those carry over to other hardware, and each part closes with how the idea applies to inference at fleet scale. The parts follow the order in which the bottlenecks showed up: hardware limits, tuning knobs, caching, quantization, attention architecture, speculative decoding, memory topology, and finally the assembled system.

The workload: an agent is not a chatbot

A coding agent runs a loop. Every turn, it sends the model:

  • the system prompt (instructions, tool definitions, skills),
  • the entire conversation so far, including every command output,

and the model returns a short reply, usually a single tool call.

Inference has two phases with different physics:

Phase What happens Bottleneck on a CPU Analogy
Prefill (reading) All prompt tokens are processed in parallel as big matrix-matrix multiplies Compute: how many multiply-adds per second the cores can do Speed-reading a whole page at once
Generation (writing) One token at a time. Each one requires streaming the active weights from RAM Memory bandwidth: how many GB/s RAM can deliver Writing word by word, re-checking a reference book for each word

A chatbot reads ~50 tokens and writes ~500. An agent reads thousands to tens of thousands and writes ~50–300 per step, dozens of times per task. It also has a worst case: compaction. When the context window fills up, the agent asks the model to summarize the entire history, which is a cold read of 18–24K tokens.

Lesson: Optimize for the traffic you actually have. For agents that means prefill throughput, prompt-cache hit rate, and how gracefully speed degrades as context grows. Empty-context tokens/sec, the number on every leaderboard, is the least relevant number.

Know your silicon: what this CPU can and can't do

Before touching a model, I mapped the machine, because every later surprise traces back to this diagram.

Property Value Why it matters for LLMs
Cores / threads 8 / 16 (SMT) SIMD units are per core. A second thread on the same core shares them
SIMD AVX2 + FMA + F16C, 256-bit The quantized matmul kernels run here
Missing AVX-512, AVX-VNNI No single-instruction int8 dot product. Every int8 multiply-add takes a multi-instruction sequence
Caches 32 KB L1d + 512 KB L2 per core, 16 MB shared L3 A ~15 GB model doesn't fit in cache, so everything streams from RAM
Memory DDR4-3200, 16 GB SO-DIMM + 8 GB soldered (mismatched) Theoretical peak 51.2 GB/s, but only 16 GB can be dual-channel. The rest runs at single-channel speed; Part 7 measures exactly where
GPU Integrated Vega, shares system RAM Adds compute but no extra bandwidth
Power class 15 W-class "U" part Measured package power swings between 15 and 42 W; it heats up fast

The napkin math that framed everything

Generation ceiling = memory bandwidth ÷ bytes read per token.

  • The best measured weight-streaming bandwidth from the kernel tests (Part 4) was ~30 GB/s (28–31 across runs), about 58% of the theoretical 51.2.
  • A dense 27B model at ~3.6 bits per weight is ~12 GB per token → ceiling of ~2.5 tok/s (napkin math).
  • A Mixture-of-Experts model with ~3.3B active parameters at the same bit width is ~1.5 GB per token → ceiling of ~20 tok/s (napkin math).
  • The MoE model I started with measured 17.0 tok/s, about 85% of that ceiling.

Methodology note: my first estimate of the denominator was 33 GB/s, from a kernel benchmark that reused one ~25 MB matrix against a 16 MB L3 cache, so part of every pass came from cache. Rerunning it with enough copies to force every read out to RAM gave 28–31 GB/s (Part 4 has the details). Bytes per token is approximate too: the embedding table, for instance, is a single-row lookup per token, not a full read. So read the efficiency percentages in this series as ±10 points. The conclusion doesn't depend on them: dense is hopeless, MoE is viable.

Prefill ceiling = how fast the cores can multiply.

  • Zen 3 has two 256-bit FMA units per core. At the 2.8 GHz cap that's roughly ~717 GFLOPS of fp32 across 8 cores (spec arithmetic).
  • The quantized kernels actually work in int8. Without VNNI, each int8 multiply-accumulate is a two- or three-instruction chain on AVX2 (multiply pairs into 16-bit, widen to 32-bit, accumulate).
  • The best measured kernel hit 774 GFLOPS (q4_K). That beats the fp32 figure because int8 packs four values into each 32-bit lane, so the fp32 number is a reference point, not the ceiling for integer kernels. It's respectable, but well short of what a VNNI-capable CPU would do with the same code.

Lesson: Write down the roofline before you benchmark anything: the bandwidth ceiling for generation and the compute ceiling for prefill. It tells you which model shapes are hopeless (dense 27B+) and which are viable (MoE with ~3B active) before you download a single gigabyte. It also tells you when to stop tuning: once you're within a few tens of percent of the ceiling, flags won't close the gap. Measure the denominator with a working set much larger than the last-level cache, or the ceiling will flatter you: mine was inflated by 10% until I did.

Model shape: Mixture of Experts

A Mixture-of-Experts (MoE) model is like a large hospital: many specialists, but each patient only sees a handful. Qwen3.5-35B-A3B, for example, has 256 experts per layer and routes each token to 8 of them (plus one shared expert). It holds 35B parameters of knowledge but touches only ~3.6B per token.

That maps exactly onto the roofline: per-token bandwidth cost scales with active parameters, while knowledge scales with total parameters. The price is that the whole model must fit in RAM. On a 24 GB machine that means ~3–4 bits per weight.

First shortlist (CPU, 8 threads, empty context):

Model Prefill (pp512) Generation (tg128)
gpt-oss-20b (MXFP4 quantization) 49.9 tok/s 10.2 tok/s
Qwen3-Coder-30B-A3B (UD-Q3_K_XL quantization) 69.7 tok/s 15.4 tok/s

gpt-oss lost even though it's the smaller model. The reason turned out to be its quantization format, not its architecture (Part 4).

Lesson: On bandwidth-bound hardware, active parameter count is the cost and total parameter count is the capability. MoE is the only way to get 30B-class knowledge at interactive speed on a laptop CPU.

Beyond the laptop

This is the same arithmetic I use to size GPU serving. Decode is bounded by memory bandwidth ÷ bytes per token, whether that bandwidth is HBM or DDR4, and prefill is bounded by matmul throughput. What changes between a laptop and a fleet is the workload mix. Agent traffic is prefill-heavy and long-context, which is why the industry moved toward prefix caching and disaggregated prefill/decode serving. The leaderboard number, single-stream decode at empty context, describes almost none of that traffic.
