<p>Part 1 of 8 in the series. Next: Part 2: Most Tuning Knobs Don't Matter (and Some Backfire) (coming soon).</p>
</blockquote>
<hr>
<p>Over three days I turned an AMD Ryzen 7 7730U laptop (8 Zen 3 cores, 24 GB DDR4-3200, integrated graphics only) into a local coding-agent host: the terminal agent <strong>pi</strong> talking to a <strong>llama.cpp</strong> server running a 35-billion-parameter model on the CPU alone. This series is the field notes. Almost every win came from understanding the bottleneck rather than from tuning flags, so this first part covers the groundwork: the workload, the silicon, and the model shape the two of them allow.</p>
<h3 id="the-mindset">The mindset</h3>
<p>I approached this like any capacity problem in production inference. Three rules held throughout:</p>
<ol>
<li><strong>Characterize the workload before choosing the system.</strong> An agent's traffic pattern is nothing like a chatbot's.</li>
<li><strong>Know which resource is saturated.</strong> On a CPU, the bottleneck is either compute (FLOPs), memory bandwidth (GB/s), or heat (watts). Each phase of inference hits a different one.</li>
<li><strong>Every claim gets a benchmark, including the folklore.</strong> Several widely repeated tips made things worse here.</li>
</ol>
<p>Each section in this series ends with the <strong>lesson</strong> it taught, since those carry over to other hardware, and each part closes with how the idea applies to inference at fleet scale. The parts follow the order in which the bottlenecks showed up: hardware limits, tuning knobs, caching, quantization, attention architecture, speculative decoding, memory topology, and finally the assembled system.</p>
<hr>
<h3 id="the-workload-an-agent-is-not-a-chatbot">The workload: an agent is not a chatbot</h3>
<p>A coding agent runs a loop. Every turn, it sends the model:</p>
<ul>
<li>the system prompt (instructions, tool definitions, skills),</li>
<li>the entire conversation so far, including every command output,</li>
</ul>
<p>and the model returns a short reply, usually a single tool call.</p>
<figure><img src="/writing/local-llm-laptop-cpu/part-1-fig1.png" alt="Sequence diagram" loading="lazy" /></figure>

<p>Inference has two phases with different physics:</p>
<div class="table-scroll"><table>
<thead>
<tr>
<th>Phase</th>
<th>What happens</th>
<th>Bottleneck on a CPU</th>
<th>Analogy</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Prefill</strong> (reading)</td>
<td>All prompt tokens are processed in parallel as big matrix-matrix multiplies</td>
<td><strong>Compute</strong>: how many multiply-adds per second the cores can do</td>
<td>Speed-reading a whole page at once</td>
</tr>
<tr>
<td><strong>Generation</strong> (writing)</td>
<td>One token at a time. Each one requires streaming the active weights from RAM</td>
<td><strong>Memory bandwidth</strong>: how many GB/s RAM can deliver</td>
<td>Writing word by word, re-checking a reference book for each word</td>
</tr>
</tbody>
</table></div>
<p>A chatbot reads ~50 tokens and writes ~500. An agent reads <strong>thousands to tens of thousands</strong> and writes ~50–300 per step, dozens of times per task. It also has a worst case: <strong>compaction</strong>. When the context window fills up, the agent asks the model to summarize the entire history, which is a cold read of 18–24K tokens.</p>
<blockquote>
<p><strong>Lesson:</strong> Optimize for the traffic you actually have. For agents that means prefill throughput, prompt-cache hit rate, and how gracefully speed degrades as context grows. Empty-context tokens/sec, the number on every leaderboard, is the least relevant number.</p>
</blockquote>

<p>Before touching a model, I mapped the machine, because every later surprise traces back to this diagram.</p>
<figure><img src="/writing/local-llm-laptop-cpu/part-1-fig2.png" alt="Flowchart" loading="lazy" /></figure>

<h4 id="the-napkin-math-that-framed-everything">The napkin math that framed everything</h4>
<p><strong>Generation ceiling</strong> = memory bandwidth ÷ bytes read per token.</p>
<ul>
<li>The best measured weight-streaming bandwidth from the kernel tests (Part 4) was <strong>~30 GB/s</strong> (28–31 across runs), about 58% of the theoretical 51.2.</li>
<li>A <strong>dense 27B</strong> model at ~3.6 bits per weight is ~12 GB per token → ceiling of <strong>~2.5 tok/s</strong> <em>(napkin math)</em>.</li>
<li>A <strong>Mixture-of-Experts</strong> model with ~3.3B active parameters at the same bit width is ~1.5 GB per token → ceiling of <strong>~20 tok/s</strong> <em>(napkin math)</em>.</li>
<li>The MoE model I started with measured <strong>17.0 tok/s</strong>, about 85% of that ceiling.</li>
</ul>
<blockquote>
<p><strong>Methodology note:</strong> my first estimate of the denominator was 33 GB/s, from a kernel benchmark that reused one ~25 MB matrix against a 16 MB L3 cache, so part of every pass came from cache. Rerunning it with enough copies to force every read out to RAM gave 28–31 GB/s (Part 4 has the details). Bytes per token is approximate too: the embedding table, for instance, is a single-row lookup per token, not a full read. So read the efficiency percentages in this series as ±10 points. The conclusion doesn't depend on them: dense is hopeless, MoE is viable.</p>
</blockquote>
<p><strong>Prefill ceiling</strong> = how fast the cores can multiply.</p>
<ul>
<li>Zen 3 has two 256-bit FMA units per core. At the 2.8 GHz cap that's roughly <strong>~717 GFLOPS</strong> of fp32 across 8 cores <em>(spec arithmetic)</em>.</li>
<li>The quantized kernels actually work in <strong>int8</strong>. Without VNNI, each int8 multiply-accumulate is a two- or three-instruction chain on AVX2 (multiply pairs into 16-bit, widen to 32-bit, accumulate).</li>
<li>The best measured kernel hit <strong>774 GFLOPS</strong> (q4_K). That beats the fp32 figure because int8 packs four values into each 32-bit lane, so the fp32 number is a reference point, not the ceiling for integer kernels. It's respectable, but well short of what a VNNI-capable CPU would do with the same code.</li>
</ul>
<figure><img src="/writing/local-llm-laptop-cpu/part-1-fig3.png" alt="Flowchart" loading="lazy" /></figure>

<blockquote>
<p><strong>Lesson:</strong> Write down the roofline before you benchmark anything: the bandwidth ceiling for generation and the compute ceiling for prefill. It tells you which model shapes are hopeless (dense 27B+) and which are viable (MoE with ~3B active) before you download a single gigabyte. It also tells you when to stop tuning: once you're within a few tens of percent of the ceiling, flags won't close the gap. Measure the denominator with a working set much larger than the last-level cache, or the ceiling will flatter you: mine was inflated by 10% until I did.</p>
</blockquote>
<hr>
<h3 id="model-shape-mixture-of-experts">Model shape: Mixture of Experts</h3>
<p>A <strong>Mixture-of-Experts (MoE)</strong> model is like a large hospital: many specialists, but each patient only sees a handful. Qwen3.5-35B-A3B, for example, has <strong>256 experts per layer and routes each token to 8 of them</strong> (plus one shared expert). It holds 35B parameters of knowledge but touches only ~3.6B per token.</p>
<figure><img src="/writing/local-llm-laptop-cpu/part-1-fig4.png" alt="Flowchart" loading="lazy" /></figure>

<p>That maps exactly onto the roofline: per-token bandwidth cost scales with <em>active</em> parameters, while knowledge scales with <em>total</em> parameters. The price is that the <strong>whole</strong> model must fit in RAM. On a 24 GB machine that means ~3–4 bits per weight.</p>
<p>First shortlist (CPU, 8 threads, empty context):</p>
<div class="table-scroll"><table>
<thead>
<tr>
<th>Model</th>
<th>Prefill (pp512)</th>
<th>Generation (tg128)</th>
</tr>
</thead>
<tbody>
<tr>
<td>gpt-oss-20b (MXFP4 quantization)</td>
<td>49.9 tok/s</td>
<td>10.2 tok/s</td>
</tr>
<tr>
<td>Qwen3-Coder-30B-A3B (<code>UD-Q3_K_XL</code> quantization)</td>
<td><strong>69.7 tok/s</strong></td>

</tr>

<p>gpt-oss lost even though it's the smaller model. The reason turned out to be its quantization format, not its architecture (Part 4).</p>
<blockquote>
<p><strong>Lesson:</strong> On bandwidth-bound hardware, <strong>active</strong> parameter count is the cost and <strong>total</strong> parameter count is the capability. MoE is the only way to get 30B-class knowledge at interactive speed on a laptop CPU.</p>
</blockquote>
<h3 id="beyond-the-laptop">Beyond the laptop</h3>
<p>This is the same arithmetic I use to size GPU serving. Decode is bounded by memory bandwidth ÷ bytes per token, whether that bandwidth is HBM or DDR4, and prefill is bounded by matmul throughput. What changes between a laptop and a fleet is the workload mix. Agent traffic is prefill-heavy and long-context, which is why the industry moved toward prefix caching and disaggregated prefill/decode serving. The leaderboard number, single-stream decode at empty context, describes almost none of that traffic.</p>
